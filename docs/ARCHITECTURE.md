# Architecture

## 1. Purpose

`@ozvix/connector-vkid` is a **social connector for Logto OSS** that adds "Continue with VK ID" to a
self-hosted Logto instance. It implements the modern VK ID authorization-code flow with PKCE and
maps the VK ID profile onto Logto's `SocialUserInfo`.

It is a connector, not an identity provider: Logto remains the only issuer. The connector is a
small, side-effect-free library that Logto calls once per HTTP request during an authentication
interaction.

Target environment:

- Logto OSS **1.46.0**, official image `svhd/logto:1.46.0`, PostgreSQL, Caddy in front.
- Public endpoint `https://auth.example.com`, admin `https://auth-admin.example.com`.
- Social-only sign-in (no username/password registration), Yandex ID already enabled.
- Applications (your OIDC applications and others) consume Logto through OIDC and are **not** affected by this
  connector: the OIDC issuer, client registrations and tokens do not change.

## 2. Where the connector sits

```
┌──────────┐   1. "Continue with VK ID"      ┌─────────────────────────┐
│ Browser  │ ──────────────────────────────▶ │ Logto Experience (UI)   │
│          │                                 │ auth.example.com           │
│          │ ◀──── 2. redirect to VK ID ──── │  POST /api/experience   │
│          │                                 └───────────┬─────────────┘
│          │                                             │ getAuthorizationUri(state, redirectUri)
│          │                                 ┌───────────▼─────────────┐
│          │                                 │ connector (this repo)   │
│          │                                 │ - mint PKCE verifier    │
│          │                                 │ - setSession(vk_*)      │
│          │                                 └───────────┬─────────────┘
│          │   3. GET id.vk.ru/authorize?…               │
│          │ ──────────────────────────────────────────▶ │ VK ID
│          │ ◀── 4. 302 /callback/<connector-id>?code&state&device_id
│          │                                             │
│          │   5. Logto submits connectorData             │
│          │ ──────────────────────────────────────────▶ │ Logto core
│          │                                 ┌───────────▼─────────────┐
│          │                                 │ connector               │
│          │                                 │ - read session          │
│          │                                 │ - POST /oauth2/auth     │──▶ VK ID token endpoint
│          │                                 │ - POST /oauth2/user_info│──▶ VK ID profile
│          │                                 │ - map to SocialUserInfo │
│          │                                 └───────────┬─────────────┘
│          │   6. Logto creates/links the user,          │
│          │      issues its own OIDC tokens             │
└──────────┘
```

The connector never sees Logto's own tokens, never writes to Logto's database and has no
configuration of its own beyond the connector row in Logto.

## 3. Request flow in detail

### 3.1 `getAuthorizationUri(payload, setSession)`

Logto passes `{ state, redirectUri, connectorId, connectorFactoryId, jti, headers, scope? }`.
`state` is generated by the Logto client; `redirectUri` is Logto's callback URL.

1. Read and validate the connector config from Logto (`validateConfig(config, vkidConfigGuard)`).
2. Generate a PKCE verifier: 32 CSPRNG bytes → 43-character unpadded base64url (RFC 7636 allows
   43–128).
3. Derive `code_challenge = BASE64URL(SHA256(verifier))` (`S256`).
4. Persist `{ vk_code_verifier, vk_redirect_uri, vk_state }` in the Logto connector session.
5. Return `https://id.vk.ru/authorize?client_id=…&redirect_uri=…&state=…&scope=…&response_type=code&code_challenge=…&code_challenge_method=S256`.

Why the redirect URI and state are persisted: VK ID requires both at the **token** endpoint, but
they only exist on the authorization side. Logto's callback delivers just `code`, `state` and
`device_id`; nothing else is available later.

The `vk_` prefix keeps the connector's keys from colliding with the session keys Logto core writes
(`state`, `redirectUri`, `connectorId`, `connectorFactoryId`, `jti`) — Logto's session guard accepts
arbitrary extra keys, so both sets coexist.

### 3.2 Callback validation

VK ID redirects to `redirect_uri?code=…&state=…&device_id=…` (+ optional `type=code_v2`).
`redirect_uri` is **never** echoed (verified against six official VK sources,
`docs/research/VK-ID-PROTOCOL.md` §3). The connector therefore requires only `code` and
`device_id`, treats `state` as optional, and reconstructs the redirect URI from the session.

Validation order matters:

1. Session shape (`zod`) → `InvalidRequestParameters` if missing/expired/corrupt.
2. Provider `error` object → `AuthorizationFailed` (Logto core already maps `access_denied` before
   the connector runs; the connector repeats the check so it is correct standalone).
3. Callback shape → `InvalidRequestParameters`.
4. `state` binding: a present callback `state` must equal the session `vk_state`.
5. Only then is any network request made.

### 3.3 Token exchange

`POST https://id.vk.ru/oauth2/auth`, `application/x-www-form-urlencoded`:

| Parameter       | Source                                    |
| --------------- | ----------------------------------------- |
| `grant_type`    | constant `authorization_code`             |
| `code`          | callback                                  |
| `code_verifier` | session (`vk_code_verifier`)              |
| `client_id`     | config                                    |
| `service_token` | config, **only** for confidential VK apps |
| `device_id`     | callback                                  |
| `redirect_uri`  | session (`vk_redirect_uri`)               |
| `state`         | session (`vk_state`)                      |

There is deliberately **no `client_secret`**: VK ID's token exchange has no such parameter; the
"protected key" is for client-side SDKs, and confidential applications use `service_token` from an
allow-listed IP.

The response is validated by a lenient guard — `access_token` is mandatory, everything else
(`refresh_token`, `id_token`, `expires_in`, `scope`, `token_type`, `user_id`, `state`) is optional,
because VK ID omits some of them depending on the application type.

Two cross-checks follow:

- non-empty `state` in the response must equal the session state;
- `user_id` (number in the token response) must equal `user.user_id` (string in the profile),
  otherwise the access token and the profile belong to different users → `SocialAccessTokenInvalid`.

### 3.4 Profile

`POST https://id.vk.ru/oauth2/user_info?client_id=…` with body `access_token=…` — the shape used by
the official `vkid-web-sdk` and the Web/iOS/Android no-SDK guides. Response: `{ "user": { … } }`.

Mapping (`src/profile.ts`):

| Logto field | VK ID source                                | Rule                                                                                                      |
| ----------- | ------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `id`        | `user.user_id`                              | string, stable subject; never derived from mutable fields                                                 |
| `name`      | `first_name` + `last_name` (+ `patronymic`) | joined, whitespace-collapsed, control characters stripped, ≤256 chars                                     |
| `avatar`    | `avatar`                                    | must be an absolute `http(s)` URL, otherwise dropped                                                      |
| `email`     | `email`                                     | only when `syncEmail` is enabled; validated; lower-cased                                                  |
| `phone`     | `phone`                                     | only when `syncPhone` is enabled; normalized to E.164 (`79001234567` → `+79001234567`), otherwise dropped |

`rawData` is deliberately not populated: it would copy the entire VK profile (including e-mail and
phone that may not have been synced) into the Logto user record and the Admin Console.

### 3.5 `getUserInfo` vs `getTokenResponseAndUserInfo`

Logto core calls exactly one of them per authentication:

- token storage disabled → `getUserInfo(data, getSession)` → `SocialUserInfo`;
- token storage enabled **and** `metadata.isTokenStorageSupported` **and** the connector exposes
  `getTokenResponseAndUserInfo` → `{ tokenResponse, userInfo }`, and Logto encrypts and stores the
  token set in its Secret Vault.

Both share one pipeline (`handleCallback`) so their behaviour cannot diverge.
`tokenResponse` is rebuilt from an allow-list of fields; VK's `state` and `user_id` echoes are not
forwarded, and `access_token`/`refresh_token` never appear in any log line, error payload or
returned diagnostic.

## 4. Module layout

| File              | Responsibility                                                                   |
| ----------------- | -------------------------------------------------------------------------------- |
| `src/index.ts`    | Connector factory, session handling, callback pipeline, error mapping            |
| `src/constant.ts` | Endpoints, defaults, `ConnectorMetadata` and Admin Console form items            |
| `src/types.ts`    | Zod guards: config, callback, provider error, token response, user info, session |
| `src/pkce.ts`     | `code_verifier` / `code_challenge` (S256) on `node:crypto`                       |
| `src/http.ts`     | Form POST transport, timeout and error taxonomy                                  |
| `src/client.ts`   | VK ID API client: authorize URL, code exchange, profile                          |
| `src/profile.ts`  | `SocialUserInfo` mapping and identifier policies                                 |

The build (`tsup`) emits a single ESM file, `lib/index.js`, plus `lib/index.d.ts`. Only
`@logto/connector-kit` and `zod` stay external, and both are already inside the Logto image — the
connector adds no runtime package to the container.

## 5. Error taxonomy

| Condition                                                            | Thrown                                        | Logto surfaces                                                       |
| -------------------------------------------------------------------- | --------------------------------------------- | -------------------------------------------------------------------- |
| Session missing/expired/corrupt                                      | `InvalidRequestParameters`                    | 400 `connector.invalid_request_parameters`                           |
| Callback without `code`/`device_id`                                  | `InvalidRequestParameters`                    | 400                                                                  |
| Callback `state` mismatch                                            | `InvalidRequestParameters`                    | 400                                                                  |
| Token-response `state` mismatch                                      | `InvalidRequestParameters`                    | 400                                                                  |
| VK callback carries `error`                                          | `AuthorizationFailed`                         | 401 `connector.authorization_failed`                                 |
| Token endpoint 4xx (bad/expired code, PKCE mismatch, wrong redirect) | `SocialAuthCodeInvalid`                       | 401 `connector.social_auth_code_invalid`                             |
| Token endpoint 5xx                                                   | `General`                                     | 500 `connector.general`                                              |
| Token response not matching schema / not JSON                        | `InvalidResponse`                             | 400/500 `connector.invalid_response`                                 |
| Profile endpoint 401/403                                             | `SocialAccessTokenInvalid`                    | 401 `connector.social_invalid_access_token`                          |
| Profile endpoint 5xx                                                 | `General`                                     | 500                                                                  |
| Profile not matching schema / not JSON                               | `InvalidResponse`                             | 400/500                                                              |
| Token subject ≠ profile subject                                      | `SocialAccessTokenInvalid`                    | 401                                                                  |
| Invalid connector config                                             | `InvalidConfig`                               | 400 `connector.invalid_config` (from `validateConfig`)               |
| Timeout                                                              | `Error{ name:'TimeoutError', request:{url} }` | **502** `connector.social_provider_unreachable`, `reason: ETIMEDOUT` |
| Network failure (DNS/TLS/reset)                                      | provider `TypeError` rethrown untouched       | **502** `connector.social_provider_unreachable`                      |

Two deliberate choices:

- **Transport failures are not wrapped.** Logto 1.46.0 inspects the thrown error
  (`describeTransportFailure()`), and only an unwrapped network error becomes the documented 502
  "social provider unreachable" instead of a misleading 500 "internal error".
- **Timeout is shaped like `ky`'s `TimeoutError`** (`name === 'TimeoutError'` and a `request.url`).
  That is the duck-typed contract Logto's detector recognises. Logto reduces the URL to
  origin+path before logging, so a query string (which can contain a service token) never reaches
  the log.

## 6. Integration contracts with Logto 1.46.0

Verified against the real image and the `v1.46.0` source
(`docs/research/LOGTO-146-COMPAT.md`):

| Contract             | Value                                                                                                                                                    |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Connector Kit        | `@logto/connector-kit` **5.2.0** in the 1.46.0 image; this package declares `^5.2.0` because the loader enforces `semver.satisfies(installed, declared)` |
| Package name         | must start with `connector-`, or be `@scope/connector-…` — the loader filters on `package.json.name`                                                     |
| Entry point          | `<connector dir>/lib/index.js`, ESM default export function                                                                                              |
| Discovery            | runtime scan of `/etc/logto/packages/core/connectors`, one directory per connector                                                                       |
| Session              | `setSession(object)` during authorize, `getSession()` at callback; read-once (Logto clears it after use), TTL = interaction session                      |
| `state` verification | **not** performed server-side by Logto core; the connector's own binding is the server-side CSRF check                                                   |
| Social user info     | validated by `socialUserInfoGuard` (`id` required; `email`, `phone`, `name`, `avatar`, `rawData` optional strings)                                       |
| Token storage        | requires `metadata.isTokenStorageSupported` + connector setting + `getTokenResponseAndUserInfo` + a non-empty `access_token`                             |
| Refresh              | optional `getAccessTokenByRefreshToken`; **not implemented here** (see §7)                                                                               |
| Connector id         | `vk-universal`, target `vk`, type `Social` — kept from upstream so an in-place migration does not orphan `connectorId` rows                              |

## 7. Deliberate non-goals

- **No refresh-token grant.** VK ID rotates refresh tokens and requires the `device_id` that was
  issued during authorization; Logto's token set does not persist it, so a refresh path could only
  be half-working. Token storage still gives consumers a 1-hour access token.
- **No `id_token` validation.** VK ID is not an OIDC provider (no discovery, no JWKS, and VK's own
  example is inconsistent about the signing algorithm). Identity comes from `user_info` over TLS
  with a token obtained directly from VK ID, so the JWT is not a trust anchor here.
- **No silent e-mail/phone linking.** `syncEmail`/`syncPhone` default to `false`; enabling them is
  an explicit administrator decision, documented as an account-linking risk.
- **No custom HTTP client** (`ky`/`got`): platform `fetch` removes a dependency and gives exact
  control over the timeout/error shape.
- **No `state` regeneration.** The connector forwards Logto's `state` unchanged; rewriting it would
  break Logto's own client-side check and VK's documented round-trip requirement.

## 8. Relationship to the upstream connector

This project is derived from `@workingbit/connector-vk@0.0.4` (MPL-2.0), itself derived from Logto's
GitHub connector. `src/constant.ts`, `src/types.ts` and `src/index.ts` carry upstream content in
rewritten form; the remaining modules are new. The provenance chain, the audited findings and the
list of modifications are in [`SECURITY-AUDIT.md`](SECURITY-AUDIT.md) and [`../NOTICE`](../NOTICE).

What was kept because it was already correct: the VK ID endpoints, the default scope, PKCE with
`S256`, storing the verifier in the Logto session, and the `vk-universal` factory id.

## 9. Extending

- **New VK ID response field**: add it to `vkUserGuard` (optional) and to `mapVkUser`; keep
  `rawData` empty unless you accept the PII duplication.
- **New scope**: no code change — set it in the connector config. A value is only returned by VK ID
  when the scope is both enabled in the VK app dashboard _and_ requested.
- **VK ID protocol change**: `src/constant.ts` for paths, `src/client.ts` for request shapes,
  `src/types.ts` for validation. Nothing else should need to move.
- **VK API host change**: the `apiBaseUrl` setting exists for mirrors and for the local mock server;
  production should stay on the default `https://id.vk.ru`.
